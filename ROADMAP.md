# ROADMAP: микросервисы на Go — «Пиццерия»

Пять сервисов на двух протоколах, PostgreSQL, Kafka, Redis и полная наблюдаемость.
Всё пишем руками и на предметной области: доставка пиццы.

## Договорённости

- **Тема:** доставка пиццы. Заказ → склад ингредиентов → оплата → кухня готовит → уведомление.
- **Темп:** 5–7 часов в неделю, ориентировочно 4–5 месяцев. Не гоним.
- **Формат:** код пишешь ты. Я даю карту проекта, карту задачи (какие файлы и контракты нужны),
  ревью и наводки при застревании. Готовый код от меня — только для сборки и конфигов
  (Makefile, buf.yaml, docker-compose, go.mod, .gitignore, миграции) и для сравнения, когда
  мы уже разобрались, где ошибка.
- **Правила:** я не правлю твои файлы без просьбы. Тесты пишем сразу, не «потом».
  Сверка раз в неделю: сделано / непонятно / дальше.
- **Словарь слоёв:** API-модель — что приходит по сети; домен — пиццерия в чистом виде;
  storage — строки в PostgreSQL. Держим их раздельно.

## Ритм работы

Три уровня, чтобы не путаться в масштабе:

| Уровень | Размер | Как оформляется |
|---|---|---|
| Задача — один пункт чеклиста этапа | 0.5–2 часа | ветка + PR, один коммит в `main` |
| Этап — блок из 5–10 задач | 5–15 часов, то есть 1–2 недели | задачи идут своими PR, этап закрывается тегом `v0.x` |
| Веха — 2–3 этапа | около месяца | тег `v0.x` и запись в README, что уже работает |

**5–7 часов — это недельный бюджет, а не размер этапа.** Один этап — примерно неделя-две.
Перед началом этапа раскладываем его на задачи: получаешь список шагов, каждый на один-два
вечера, и после каждого шага — коммит и PR. Так видно прогресс даже в короткий вечер.

**Этап — единица плана, а не единица git.** Ветка живёт одну задачу, этап живёт в роадмапе
и закрывается тегом. Раньше было «один этап — одна ветка», и это правило конфликтовало
само с собой: squash-мерж превращал весь этап в один коммит, хотя договаривались
про «один коммит — одна задача».

ТЗ каждой задачи — файл в `tasks/stage-N/`, номер в имени совпадает с номером задачи
в раскладке этапа. Задача приезжает в репозиторий вместе с кодом, и по истории видно,
что именно от тебя требовалось в этом коммите. Оглавление — `tasks/README.md`.

## Git: ветки, коммиты, PR

В `main` напрямую не коммитим и не пушим, даже когда разработчик один. `main` —
единственная долгоживущая ветка, и она всегда зелёная: ветка живёт одну задачу и умирает
в день мержа. Длинных веток «на этап» не держим — чем дольше ветка живёт, тем дороже
расхождение с `main`, а PR на две недели работы никто не ревьюит.

- Имя ветки — по смыслу задачи: `feat/pgx-pool`, `fix/clone-without-env`, `docs/task-branches`,
  `chore/lint-setup`. Номера этапов в имени не появляются: этап — единица плана, а не git.
- Один PR — одна задача, диф читается за 10–15 минут. Не влезает — значит, это две задачи.
- Один коммит — одна задача, сообщение в императиве и без «я сделал»:
  «добавить миграцию ингредиентов», «исправить запуск без .env».
- Перед PR должно быть чисто: `make fmt-diff` и `make lint` без замечаний, `make test-race` зелёный.
- PR в `main`: в описании — что сделано и чем проверено. Заголовок PR при squash-мерже
  становится коммитом в `main`, поэтому пишем его как сообщение коммита.
- Мерж только **squash**: один PR = один коммит в `main` = одна задача. Отменяется такой
  коммит одним `git revert`, не задевая соседей.
- После мержа ветку удаляем — и на GitHub, и локально.
- Если задача временно ломает `main`, её не мержат: доводим до зелёного или не подключаем.
  Пакет в `internal` можно влить в `main` спокойно, пока его никто не вызывает.
- Закрытый этап помечаем тегом `v0.1`, `v0.2`, ...

Полный цикл:

```bash
git switch main && git pull            # начать со свежего main
git switch -c feat/pgx-pool            # ветка под задачу
# ... задача, тесты ...
make fmt-diff && make lint && make test-race
gh pr create --fill                    # PR (gh авторизован как ramil063)
gh pr merge --squash --delete-branch   # влили и убрали ветку
git switch main && git pull
```

Защита стоит с двух сторон.

**На GitHub:** `main` защищён — прямой пуш запрещён, обязателен PR (0 обязательных апрувов,
чтобы можно было мержить самому), force-push и удаление ветки запрещены, правила действуют
и на владельца репозитория.

**Локально:** `make hooks` подключает хуки из `.githooks/`. `pre-commit` не даёт коммитить
прямо в `main`, `pre-push` не даёт туда пушить. Осознанный обход — переменные
`FORNO_ALLOW_MAIN_COMMIT=1` и `FORNO_ALLOW_MAIN_PUSH=1`.

**CI пока нет.** Поэтому «`main` всегда зелёный» держит человек: проверки гоняются локально
перед PR. Настоящий шлюз — GitHub Actions на каждый PR (сборка, линтер, тесты) и запрет
мержа при красных проверках; это отдельный шаг, когда дойдём до него руками.

## Где появится многопоточность

Отдельного этапа «горутины и каналы» не будет: это не тема на неделю, а инструмент под задачу.
По ходу проекта они встретятся здесь:

| Инструмент | Где именно | Этап |
|---|---|---|
| `chan` | корректное завершение сервиса (сигнал приходит в горутину) | с 1-го |
| `errgroup` | параллельные запросы к складу и платёжке: упал один — отменяем остальные | 3 |
| `errgroup` | проверка окружения: база, миграции и пул опрашиваются одновременно | 1 |
| `errgroup` | батч событий Kafka: N сообщений обрабатываем конкурентно, с ограничением | 8 |
| `errgroup` | корректное завершение: ждём N горутин и собираем все ошибки | 7 |
| `map` + `sync.RWMutex` | кеш ингредиентов в памяти, индекс по меню, дедупликация событий | 7, 8 |
| `sync.Once`, `atomic` | ленивая инициализация в DI, счётчики метрик | 4, 7 |
| Consumer Groups | несколько экземпляров делят поток Kafka, обработка батчами | 8 |
| `semaphore` | ограничение одновременных вызовов к внешнему сервису | 11 |

**Важно:** мьютекс защищает данные только внутри одного процесса, а реплик у сервиса будет
несколько. Поэтому за общий ресурс у нас отвечают база (`SELECT FOR UPDATE`) и Redis
(распределённая блокировка), а `map` + `sync.Mutex` — только для локального кеша. Это и есть
разница между «многопоточность в одном процессе» и распределённой системой.

Гонки ловим не глазами, а `make test-race` — он для этого и настроен.

## Контексты: какие и где

| Контекст | Где именно | Этап |
|---|---|---|
| `context.Background()` | только в `main()` и в тестах, как корень дерева — не внутри библиотечного кода | 1 |
| `context.TODO()` | временная заглушка; к концу этапа 4 в проекте не остаётся | 1–4 |
| `r.Context()` (создаёт net/http) | отменяется сам, когда клиент закрыл соединение; отмена уходит в БД и в gRPC | 3 |
| `WithCancel` | корень сервиса от сигнала ОС; отмена остальных горутин по первой ошибке | 3, 7 |
| `WithTimeout` | запрос к базе и внешним сервисам, хендлер целиком, остановка сервиса | с 1-го |
| `WithDeadline` | дедлайн всего запроса, когда он длиннее одного вызова | 10 |
| `WithValue` | только сквозные данные: `user-id`, `trace-id`; не параметры вызова | 9, 10 |
| `WithoutCancel` | дозаписать лог или метрику уже после отмены запроса | 10 |

Главное здесь: **отмену по уходу клиента создавать руками не надо** — её создаёт `net/http`,
а наша задача протащить `r.Context()` до самого низа и не потерять по пути. Проверяет это
`contextcheck` из `.golangci.yml`: `ctx` первым аргументом, `defer cancel()` всегда,
контекст не хранится в структуре, `nil` не передаётся.

## Graceful shutdown

Прописан в двух точках: базовое завершение `order-service` на этапе 3 (chi + `http.Server.Shutdown`)
и общий менеджер закрытия ресурсов в платформенной библиотеке на этапе 7. Порядок всегда такой:

1. Получили `SIGINT`/`SIGTERM` — корневой контекст сервиса отменяется (`signal.NotifyContext`).
2. Перестали принимать новое: снимаем listener у HTTP и gRPC.
3. Дождались текущих запросов — с таймаутом, иначе ждать придётся вечно.
4. Закрыли ресурсы в обратном порядке: что открыли последним — закрываем первым
   (consumer → пул базы → логгер).

### Этап 4 — Clean Architecture

- [ ] Слои API → Service → Repository → Client в каждом сервисе

**Готово, когда:** бизнес-логика отделена от транспорта и хранилища, домен не знает
ни про gRPC, ни про SQL, и любой новый человек сразу понимает, где что лежит.
