# Задача 1.6 — репозиторий склада ингредиентов

- **Этап:** 1, «PostgreSQL с самого начала: инфраструктура и хранилище»
- **Оценка:** ~1 час
- **Зависимости:** задача 1.5 (запросы через squirrel) — готова
- **Артефакт:** `services/inventory-service/internal/storage/postgres/ingredient_repository.go`
- **Готово, когда:** есть тип-репозиторий, через который создают, читают и перечисляют
  ингредиенты, и он не содержит SQL.

## Файлы

```
services/inventory-service/internal/storage/postgres/
  ingredient_repository.go   тип репозитория и его методы
```

Отдельного файла тестов нет — почему, объяснено в разделе «Тесты».

## Контракт (форма; имена можно менять)

```go
type IngredientRepository struct {
	db DBTX
}

func NewIngredientRepository(db DBTX) *IngredientRepository

func (r *IngredientRepository) Create(ctx context.Context, in CreateIngredientParams) (int64, error)
func (r *IngredientRepository) Get(ctx context.Context, id int64) (IngredientRow, error)
func (r *IngredientRepository) List(ctx context.Context, limit, offset int) ([]IngredientRow, error)
```

## Требования

1. **Никакого SQL в репозитории.** Методы вызывают готовые функции из задачи 1.5
   (`CreateIngredient`, `GetIngredient`, `ListIngredients`). Если появится соблазн написать
   `db.QueryRow("SELECT ...")` прямо здесь — значит, это место для новой функции-запроса,
   а не для репозитория.
2. **Ошибки не теряются.** Пробрасывай их без изменений или оборачивай через `%w`, чтобы
   снаружи продолжали работать `errors.Is(err, errIngredientNotFound)`,
   `errors.Is(err, errIngredientAlreadyExists)` и `errors.As(err, &pgErr)`.
3. **`DBTX` — тот же интерфейс, что в задаче 1.5.** Репозиторий не знает, что ему передали:
   пул или транзакцию. На этапе 6 это позволит прозрачно выполнить несколько операций
   в одной транзакции.
4. **Никакой бизнес-логики.** Репозиторий не решает, можно ли создать ингредиент, не
   проверяет единицы измерения и не архивирует. Это уровень сервиса (появится на этапе 2–4).
5. **Один репозиторий — одна сущность.** Здесь только ингредиенты. Остатки, склады, единицы
   измерения — отдельные репозитории, когда до них дойдёт очередь.

## Тесты

В этой задаче тестов нет — **осознанно**, а не «потом». Причина: слой не содержит логики,
он только делегирует вызовы. Тест на делегирование проверял бы реализацию
(«вызвали ли мы функцию»), а не поведение, и ломался бы от любого рефакторинга.

Настоящая проверка этого слоя — интеграционные тесты в задаче 1.7: создать через репозиторий,
прочитать через репозиторий, перечислить. Там же проверятся `ErrNoRows`, уникальность
и nullable-поля на живой базе.

## Как проверю

- [ ] `make fmt-diff`, `make lint`, `make test-race` — зелёные (старые тесты не сломались)
- [ ] в `ingredient_repository.go` нет ни одной SQL-строки и ни одного `sq.` — прочитаю глазами
- [ ] методы вызывают функции из `ingredient.go`, а не повторяют их код
- [ ] `errors.Is` для `errIngredientNotFound` и `errIngredientAlreadyExists` продолжает
      работать после обёртки в репозитории
