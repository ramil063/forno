# Задача 1.3 — cmd/checkenv: параллельная проверка окружения

- **Этап:** 1, «PostgreSQL с самого начала: инфраструктура и хранилище»
- **Оценка:** ~1.5–2 часа
- **Зависимости:** задача 2 (пул `pgx`) — оттуда берётся конструктор и `Ping`.
- **Артефакт:** `services/inventory-service/internal/checkenv/checkenv.go` (+ тесты)
  и `services/inventory-service/cmd/checkenv/main.go`
- **Готово, когда:** одна команда говорит, что с окружением — и называет, что именно сломано,
  а не просто «ошибка».

Это первая задача, где появляется `errgroup` (см. `ROADMAP.md`, раздел про многопоточность).

## Файлы

```
services/inventory-service/
  cmd/checkenv/main.go               тонкий: контекст с таймаутом, DSN, вызов, exit code
  internal/checkenv/checkenv.go      сами проверки; ничего не знает про os.Exit и stdout
  internal/checkenv/checkenv_test.go
```

## Проверки

**Предусловие.** Сначала создаём пул (`postgres.New`). Если он не создался — печатаем одну
понятную ошибку и выходим: при лежащей базе проверять миграции и пул нечего. Это не «проверка»,
а вход в них — так и оформи в коде.

Дальше три проверки идут параллельно.

### 1. База отвечает

`pool.Ping(ctx)` с собственным таймаутом (например, 2s). Отвечает на вопрос «соединение живо
прямо сейчас и база успевает ответить за отведённое время».

Почему это отдельная проверка, если `New` уже пинговал при старте: `New` пинговал один раз
и на этом всё, а здесь проверка имеет свой таймаут и свой текст в отчёте. Разница видна
в поведении: упавший `New` — это «до проверок не дошли», упавший `Ping` — «проверка не прошла,
остальные отработали».

### 2. Миграции накатаны

Проверяются две вещи вместе:

- таблицы схемы на месте: `SELECT to_regclass('public.ingredients') IS NOT NULL` — и так
  для `units`, `warehouses`, `ingredients`, `ingredient_stock`. Функция `to_regclass` возвращает
  `NULL`, если объекта нет, поэтому проверка укладывается в один запрос;
- есть применённая миграция: `SELECT version_id, is_applied FROM goose_db_version
  ORDER BY id DESC LIMIT 1` — нужно `is_applied = true` и версия не 0.

`version_id = 0` — служебная запись goose «до всяких миграций», она есть даже в пустой базе.
Именно поэтому проверка «таблица `goose_db_version` существует» ничего не доказывает, а база
после `make migrate-down` её имеет.

Текст ошибки должен называть конкретику: «нет таблицы `ingredient_stock`» или «последняя
применённая версия — 0», а не «ошибка проверки миграций».

### 3. Пул отдаёт соединение

Самая содержательная из трёх. `Ping` выше проверяет, что база отвечает; эта проверка — что
**пул** реально выдаёт соединение из своего набора и забирает его обратно. Именно это
происходит при каждом настоящем запросе, поэтому и проверять надо это.

Порядок такой:

1. `conn, err := pool.Acquire(ctx)` — берём соединение из пула. Если все соединения заняты,
   `Acquire` **ждёт** освобождения, поэтому ему нужен свой таймаут (например, 2s) и понятный
   текст ошибки: «не дождались свободного соединения за 2s».
2. `defer conn.Release()` — возвращаем соединение в пул. Не `Close`: `Release` — «верни
   в набор», `Close` — «закрой физическое соединение». Жизнью соединений управляет пул,
   а закрытый руками он теряет из учёта. И если `Release` забыть, соединение «утечёт»:
   пул будет считать его занятым, и после нескольких запусков `Acquire` начнёт ждать
   впустую.
3. Короткий запрос через это соединение, например
   `SELECT current_setting('application_name'), current_setting('statement_timeout')`.
   Он проверяет заодно то, что делали в задаче 1.2: настройки применились ко **всем**
   соединениям пула, а не только к стартовому.
4. Статистика `pool.Stat()`: `MaxConns()`, `TotalConns()`, `IdleConns()`, `AcquiredConns()`,
   плюс счётчики неудач `EmptyAcquireCount()` и `CanceledAcquireCount()`. Это снимок на момент
   вызова — значения устаревают мгновенно, и это нормально. В продакшене смотрят именно
   на эти цифры, когда «почему-то стало медленно»: много `Acquired` при маленьком `MaxConns`
   и растущий `EmptyAcquireCount` — это исчерпание пула.

Запрос можно выполнить как `conn.QueryRow(ctx, ...)`, либо через `conn.Conn().QueryRow(...)`.
Во втором случае ты получаешь `*pgx.Conn`, который нельзя использовать из нескольких горутин
одновременно; для проверки хватит первого варианта.

## Три исхода проверки: ok, fail, skip

`errgroup.WithContext` отменяет сестринские горутины, когда одна вернула ошибку. Это правильно
(«перестали долбить базу»), но у этого есть побочный эффект: отменённая проверка возвращает
`context.Canceled`, и если не различать случаи, в отчёте появится ложное падение.

Проверено на живом окружении (база жива, `make migrate-down` дважды):

```
ok ping
FAIL db: нет таблицы ingredients
FAIL pool: получение соединения отменено: context canceled   ← этого падения не было
```

Пул цел — его просто отменили раньше времени. Поэтому исходов у проверки три:

- **ok** — проверка прошла;
- **fail** — проверка нашла настоящую проблему;
- **skip** — проверку отменила ошибка соседа или истёк общий дедлайн.

Признак `skip`: ошибка проверки разворачивается в `context.Canceled`, **и** контекст группы
отменён именно как `Canceled` (`errGroupCtx.Err() == context.Canceled`). Если контекст истёк
по дедлайну (`DeadlineExceeded`) — это настоящий `fail`: проверка не успела.

`skip` не попадает в итоговую ошибку через `errors.Join` (собираются только `fail`), но
зелёным тоже не считается: проверять было нечего, потому что сначала надо починить то,
из-за чего отменили.

Если предпочитаешь вообще не отменять проверки — обойдись `errgroup.Group` без контекста,
а таймаут оставь внутри каждой проверки. Тогда `skip` не понадобится: все проверки дойдут
до конца и покажут полную картину. Минус — теряется «перестали долбить базу при первой
ошибке». Выбор за тобой, обоснуй в коммите.

## Как это устроено в продакшене (и где мы отличаемся)

Мы делаем то же самое, но чуть иначе упакованным:

- Там это обычно не CLI, а **readiness-эндпоинт** («готов принимать трафик»), который дёргает
  платформенный проб (в Kubernetes — kubelet). CLI-проверки тоже существуют, их называют
  doctor или preflight, но чаще их роль играет readiness.
- Есть разделение **liveness** («процесс жив») и **readiness** («готов работать»). Liveness
  в базу не ходит вообще: иначе упавшая база приведёт к перезапуску здоровых процессов.
  В зависимости ходят именно из readiness — ровно как здесь.
- Проверки держат **дешёвыми**: readiness — это один короткий запрос с коротким таймаутом,
  а не аудит схемы. Наш `checkenv` делает больше, потому что это команда для разработчика,
  а не проба для оркестратора.
- Метрики пула (занятые/свободные, число отказов выдать соединение) — то, что обычно выведено
  на дашборд.

К readiness мы вернёмся на этапе 7 (платформенная библиотека), к метрикам — на этапе 10.

## Требования

- Три проверки идут параллельно через `errgroup.WithContext`: упала одна — остальные
  отменяются по контексту, а не продолжают долбить базу.
- Но показать нужно **все** проблемы, а не первую. Поэтому результат каждой проверки —
  своя строка (или свой элемент) в срезе: каждая горутина пишет только в свой слот,
  `errgroup.Wait()` даёт синхронизацию, мьютекс здесь не нужен — объясни в коммите, почему.
  Итог собирается через `errors.Join`.
- Общий таймаут на всю команду (например, 10s) создаётся в `main`. В библиотеку контекст
  приходит первым аргументом.
- `os.Exit` — только в `main`. Пакет `checkenv` не знает ни про stdout, ни про код возврата:
  на этапе 7 этот же код станет health-check сервиса.
- Список проверок — данные, а не копипаста: добавить четвёртую проверку = одна строка в списке.
- Вывод: строка на проверку (имя + ok/ошибка), затем итог. Ошибки не глотать.
- Тексты ошибок по-человечески: «база недоступна: …», «миграции не накатаны: последняя
  применённая версия — 0», а не «error» и не голый `%v` от pgx.

## Тесты (сразу, не потом)

Проверки должны подменяться в тестах, без базы и без сети. Скорее всего появится маленький
интерфейс «проверка» (`Name()` + `Check(ctx) error` или функция с таймаутом) — объяви его там,
где он используется, то есть в `checkenv`.

- табличный тест с фейками: все три ок; падает вторая; падают все три → в итоговой ошибке
  три текста, а не один;
- тест на таймаут: проверка, которая спит дольше контекста, должна вернуть ошибку отмены,
  а не висеть;
- `make test-race` должен быть зелёным — здесь он ловит именно то, ради чего мы городим
  срез вместо `map`.

## Как проверю

- [ ] `make shell` → `cd services/inventory-service && go run ./cmd/checkenv` → три ok, exit 0
- [ ] в выводе видно статистику пула (максимум / всего / свободно / занято) и что
      `application_name` со `statement_timeout` доехали до соединения из пула
- [ ] `make db-down` → та же команда → внятные ошибки про базу, exit ≠ 0, без паники
      и без ожидания «до посинения»
- [ ] `make migrate-down` дважды → база жива, таблиц нет → проверка миграций падает (`fail`),
      `ping` зелёный, а `pool` помечена как пропущенная (`skip`), а не как упавшая: её отменила
      ошибка соседа. Отдельное доказательство независимости проверок
- [ ] `make migrate-up` возвращает всё на место
- [ ] `make test-race` зелёный, тесты не требуют базы
- [ ] в новом коде нет `context.Background()` вне `main` и нет `context.TODO()`
- [ ] по логу видно, что проверки идут параллельно: общее время ≈ самое долгое, а не сумма трёх
