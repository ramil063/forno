# Задача 1.4 — схема склада ингредиентов

- **Этап:** 1, «PostgreSQL с самого начала: инфраструктура и хранилище»
- **Оценка:** ~1.5 часа
- **Зависимости:** инфра этапа — goose в образе и цели `make migrate-*`. Готово, можно начинать.
- **Артефакт:** `services/inventory-service/migrations/00001_*.sql`
- **Готово, когда:** `make migrate-up` накатывает схему, `make migrate-down` возвращает базу
  в исходное состояние, а невалидные данные база не принимает.

## Как создать файл миграции

```bash
make migrate-create name=init_inventory   # создаст 00001_init_inventory.sql с шаблоном Up/Down
make migrate-up
make migrate-status
```

## Что должно храниться

- **Ингредиент:** название, единица измерения, необязательное описание (может быть `NULL` —
  это мы специально тренируем в задачах 5–6), время создания и изменения.
- **Остаток:** для каждого ингредиента — сколько лежит на складе и сколько из этого
  зарезервировано под заказы. Доступное к продаже = остаток − резерв.

## Инварианты

База обязана их держать сама, а не полагаться на код сервиса: код бывает багнутым,
сервисов будет пять, а в базу однажды полезет человек руками.

1. Остаток ≥ 0, резерв ≥ 0, **резерв ≤ остаток** — нельзя зарезервировать то, чего нет.
2. Количество — точное значение (`NUMERIC`), не `float`: `0.1 + 0.2` не должно давать хвост.
3. Единица измерения — из закрытого набора (г, мл, шт). Записать «кг», которого в наборе нет,
   база должна не дать.
4. Название ингредиента уникально и **регистронезависимо**: «Мука» и «мука» — дубликат.
5. Остаток не существует без ингредиента. Что делать при удалении ингредиента с ненулевым
   остатком — твоё решение, но обоснованное.
6. Сейчас у ингредиента одна запись остатка. Как закрепить это в схеме и не закрыть дверь
   на несколько складов в будущем?

## Сценарии доступа, под которые схема обязана быть удобной

| Сценарий | Что из этого следует для схемы |
|---|---|
| Создать ингредиент, получить ID | как генерируется ключ: базой или приложением |
| Прочитать ингредиент вместе с остатком | сколько JOIN-ов, нужен ли индекс |
| Список ингредиентов, позже поиск по названию | индекс под поиск |
| Изменить название или описание | `updated_at` должен поехать вместе с данными |
| Приход, списание, резерв, снятие резерва — атомарно, не уходя в минус | этап 6 сделает `SELECT FOR UPDATE` по строке остатка; путь до неё должен идти по индексу |

## Требования к миграции

- `-- +goose Up` и `-- +goose Down` обязательны, Down реально возвращает базу в исходное
  состояние, а не «примерно».
- Тело триггера или функции оборачивай в `-- +goose StatementBegin` / `-- +goose StatementEnd`,
  иначе goose порежет его по точке с запятой.
- Ограничения и уникальность — в DDL, а не только в коде.
- Имена: таблицы во множественном числе, snake_case, единый стиль для внешних ключей и индексов.
- Накатанную миграцию не редактируем — только новая. Проверяем цикл `up → down → up`.
- Таблицу версий `goose_db_version` создаёт сам goose: в миграции её быть не должно.

## Не делаем сейчас

JSONB-характеристики, рецепты и пиццы, партии поставок со сроком годности, цены, несколько
складов, журнал движений остатка. Если считаешь, что что-то из этого нельзя отложить — скажи,
обсудим отдельно.

## Решения за тобой

Напиши в описании к коммиту (или отдельным комментарием в файле миграции), почему выбрал так:

1. Ключ: `BIGINT` со последовательностью/`IDENTITY` или UUID — и как это сочетается
   с «вставкой с возвратом ID» из задачи 5.
2. Единица измерения: `CHECK`, enum, отдельная таблица-справочник?
3. `updated_at`: триггер, `DEFAULT` или приложение?
4. Удаление ингредиента с остатком: `RESTRICT`, `CASCADE` или запрет на уровне политики?
5. Один ингредиент — одна запись остатка: чем закреплено?

## Как проверю

- [ ] `make migrate-up` → `make psql` → `\dt`, `\d+ <таблица>`
- [ ] `make migrate-down` → таблиц нет; `up` ещё раз — без ошибок
- [ ] `make migrate-status` показывает `00001` как applied
- [ ] База не принимает: отрицательный остаток, резерв больше остатка, дубликат «мука»/«Мука»,
      единицу вне набора
- [ ] База принимает: ингредиент без описания
- [ ] Инварианты выше выражены в DDL, а не в комментариях к нему
